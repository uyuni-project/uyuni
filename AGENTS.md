# Repository Instructions

## Scope and source of truth

These instructions apply to the entire repository. If a subdirectory later
contains a more specific `AGENTS.md`, follow both files, with the nearer file
taking precedence for that subtree.

This is a large, long-lived Uyuni/Spacewalk monorepo. Treat code, manifests,
build files, and CI workflows in the target branch as authoritative.

## Repository map

- `java/`: core server, XML-RPC/API, business logic, and web application.
- `microservices/`: Java microservices and the shared
  `uyuni-java-parent` Maven parent.
- `branding/`: branding artifacts required by Java builds.
- `web/`: React/TypeScript frontend, Jest tests, Storybook, and Webpack build.
- `python/`: Python backend libraries, services, utilities, and unit tests.
- `spacecmd/`: Python command-line client.
- `susemanager/`: SUSE Manager Python modules and utilities.
- `susemanager-utils/susemanager-sls/`: Salt states and orchestration.
- `schema/`: PostgreSQL schemas, stored procedures, and upgrade scripts.
- `testsuite/`: Cucumber/Playwright acceptance and integration tests.
- `containers/`: container image definitions and container build tooling.
- `rel-eng/`: package metadata, versioning, OBS, and release tooling.
- `.github/workflows/`: the current CI definitions.

Read the README, build file, and test configuration nearest to the code being
changed. Do not assume that conventions are uniform across subsystems.

## Working practices

- Make the smallest complete change that solves the requested problem. Keep
  changes scoped to the requested subsystem; do not add speculative
  abstractions, unnecessary layers, duplicate helpers, or other code bloat.
- Do not opportunistically modernize adjacent legacy code, perform unrelated
  refactors, or mix broad formatting with a functional change.
- Optimize changes for readability. Prefer straightforward control flow,
  descriptive names, cohesive functions, and existing repository patterns over
  clever or overly generic solutions. Add comments only when intent cannot be
  made clear through the code itself.
- Keep diffs easy to review. Avoid unnecessary file churn, preserve local
  style, and separate logically distinct changes when practical.
- The repository maintains multiple active main branches for supported product
  lines as well as Uyuni development. Confirm the intended base and target
  branch before making version-sensitive changes, backports, or pull requests;
  do not assume the default branch is the correct destination.
- Preserve compatibility and existing public behavior unless the task
  explicitly changes it. Uyuni supports mixed client platforms and long-lived
  upgrade paths.
- Search for an existing implementation, helper, test pattern, or schema
  migration before adding a new one.
- Keep dependency changes intentional. Update the corresponding lockfile or
  package metadata and explain why the dependency is needed.
- Never commit credentials, tokens, hostnames from private environments, or
  generated test secrets.
- Do not run release, OBS promotion, image publication, or deployment commands
  unless the user explicitly requests that operation. These commands affect
  external infrastructure and may consume credentials from the environment.
- Do not discard unrelated worktree changes. Avoid destructive Git operations.

## Generated and derived files

Edit sources, not build output:

- Do not edit or commit `web/html/src/dist/`; `npm run build` regenerates it.
- Do not edit `schema/spacewalk/postgres/main.sql` directly. It is generated by
  `blend` from the individual SQL, package, body, and dependency files.
- Treat `susemanager/src/mgr_bootstrap_data.py` as generated; it is marked
  `DO NOT EDIT`.
- Let npm manage package lockfiles. Do not hand-edit them.

If generated output is intentionally refreshed, use the repository's generator
and include only the expected result.

## Build and test commands

Run the smallest relevant checks first. Expand to broader tests only when the
change crosses subsystem boundaries or targeted checks expose wider failures.

### Frontend

The root npm scripts delegate to `web/`, so these commands run from the
repository root:

```bash
npm --prefix web ci --ignore-scripts --save=false
npm run build
npm run test -- <test-pattern>
npm run lint
npm run tsc
```

`npm run lint` fixes ESLint findings. `npm run lint:production` runs ESLint
without auto-fixing, but it can still reorder `web/package.json`; run
`npm run sort-package -- --check` separately when reproducing CI's package
ordering check. Use npm, not Yarn. For local UI development,
`npm run proxy -- https://<server-fqdn>` starts the development proxy and
`npm --prefix web run storybook` starts Storybook.

### Java

Current local development uses Maven, with the parent and branding installed
before the main application:

```bash
mvn -f microservices/uyuni-java-parent --non-recursive install
mvn -f branding install
mvn -f java --non-recursive initialize
mvn -f java package
```

JUnit tests require the PostgreSQL test environment. Start it from `java/`
before running tests:

```bash
cd java
make -f Makefile.docker
```

Then run the owning module and test class, for example from the repository
root:

```bash
mvn -f java/core test -DskipTests=false -Dtest=<TestClass>
```

Ant/Ivy is still used by parts of the containerized integration-test workflow;
do not remove or rewrite it merely because Maven is used for local builds.

### Python

Run backend unit tests from `python/`:

```bash
python3 -m pytest test/unit/
```

Run the repository's containerized lint wrapper from the root:

```bash
./python/linting/lint.sh <path>
./python/linting/lint.sh -a
```

Python code follows Black and the repository Pylint configuration. Keep tests
isolated with mocks and temporary paths; do not make unit tests depend on a
developer's machine configuration.

For `susemanager/`, use its Makefile targets. The `unittest` target prepares
the import layout required by the tests:

```bash
make -C susemanager -f Makefile.susemanager unittest
make -C susemanager -f Makefile.susemanager pylint
```

### Database schema

Change the individual schema source files and dependency declarations. Rebuild
the aggregate from the repository root with:

```bash
make -C schema/spacewalk/postgres main
```

For an installed-schema change, inspect adjacent upgrade directories and add
the corresponding forward migration when required. Preserve ordering and
PostgreSQL compatibility; never hide migration failures.

### Acceptance tests

Acceptance tests live under `testsuite/` and use Ruby, Cucumber, Gherkin, and
Playwright. Although the repository contains local-runner documentation, the
suite depends on a large, specialized environment. Do not run acceptance tests
locally as part of routine agent validation; rely on the repository's CI
workflows for their execution.

Feature files describe user-visible behavior and must not expose CSS selectors
or implementation details. Group Ruby step definitions by domain, not by
feature file; call Ruby helpers rather than invoking one Gherkin step from
another. Use the suite's `log` helper instead of `puts`, and avoid global state
between scenarios.

## CI, packaging, and deployment

- Pull requests are coordinated by
  `.github/workflows/acceptance_tests_coordinator.yml`. Java changes may map to
  recommended tests; otherwise CI runs the larger secondary suite in shards.
- `.github/workflows/acceptance_tests_base.yml` builds and exercises a
  containerized server with several client types. A local unit test is not a
  substitute when a change affects end-to-end behavior.
- Frontend build and lint workflows use Node 22 and npm. Mirror their install
  flags when reproducing CI dependency resolution.
- Scheduled acceptance tests run every 12 hours and can reveal failures beyond
  pull-request test selection.
- Packaging and release metadata is under `rel-eng/`; package and image builds
  are published through OBS. GitHub Actions does not directly deploy merges to
  production.
- `rel-eng/release-uyuni`, `rel-eng/push-version`, and related tools are
  release-engineering operations, not routine validation commands. Do not run
  them without explicit authorization and a confirmed target project.
- Some documented commands such as `build-packages-for-obs` are external
  developer tools, not scripts shipped by this repository.

For package changelogs, follow the existing package-specific pattern. Add a
fragment beside the package changelog named
`<package>.changes.<author>.<topic>` rather than editing the consolidated
`<package>.changes` file directly.

## Change-specific expectations

- **Frontend:** keep types precise, follow existing React patterns, and add or
  update Jest tests for behavior changes. Run lint, TypeScript, and focused
  tests.
- **Java:** follow the owning module's APIs and dependency boundaries. Add
  focused JUnit tests; use the established database fixtures where needed.
- **Python:** preserve Python 3 compatibility supported by the package, use
  existing error/reporting patterns, and add pytest coverage.
- **Schema:** update source definitions and migrations together when the
  deployed database must change.
- **Salt:** preserve idempotency and platform/version guards. Test the narrowest
  applicable state or orchestration path.
- **Acceptance tests:** reuse domain steps, keep scenarios deterministic, and
  account for the suite's per-feature user and role context.
- **Documentation:** update nearby documentation when commands, configuration,
  public behavior, or operational procedures change.

Before finishing, inspect the diff for generated output, secrets, unintended
formatting, and unrelated changes. Report any checks that could not be run and
the concrete reason.
